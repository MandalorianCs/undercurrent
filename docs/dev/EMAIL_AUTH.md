# Вход по почте в Supabase: что настраивать и на чём спотыкаешься

Гайд для переноса в другой проект. Написан по следам Undercurrent —
здесь только то, что реально понадобилось, и то, что реально сломалось.

Главное, с чего начать: **встроенная отправка писем работает без всякой
настройки.** Никакого SMTP, ключей и провайдеров для первого запуска не
нужно. Работы — три переключателя, и почти всё время уходит не на них, а
на ловушки ниже.

---

## Часть 1. Три настройки, без которых не работает

Всё в дашборде проекта, раздел **Authentication**.

### 1.1. Anonymous Sign-Ins — если в продукте есть анонимный вход

`Authentication → Sign In / Providers → Allow anonymous sign-ins`

Нужно, только если приложение вызывает `signInAnonymously()`.

Различайте две вещи с обидно похожими названиями:

| | Роль в базе | Что это |
|---|---|---|
| `anon` | `anon` | запрос **без пользователя** вообще, до входа |
| анонимный вход | `authenticated` | настоящий пользователь с `auth.uid()`, но без почты |

Политики RLS пишутся на `authenticated` в обоих случаях обычного входа.
Анонимный пользователь отличается не ролью, а признаком `is_anonymous` в
токене — и различать их надо именно по нему.

### 1.2. Site URL

`Authentication → URL Configuration → Site URL`

Адрес, куда возвращает ссылка из письма. Для локальной разработки —
адрес дев-сервера, например `http://localhost:8081`.

### 1.3. Redirect URLs

Там же, ниже. Каждый адрес — **в своём поле**, не через пробел:

```
http://localhost:8081
http://localhost:8081/**
myapp://**
```

Третья строка нужна для мобильного приложения, чтобы ссылка открывала
его, а не браузер. `myapp` — значение `scheme` из `app.json`.

## Часть 2. Ловушки

Здесь всё, что стоило времени. Ни одна не описана явно в интерфейсе.

### 2.1. Переключатель не сохраняется сам

Флажок переведён, выглядит включённым — но пока не нажата зелёная
**Save changes** внизу страницы, ничего не применилось.

Проверять надо не глазами, а запросом:

```bash
curl -s -X POST "https://<ref>.supabase.co/auth/v1/signup" \
  -H "apikey: <publishable-key>" -H "Content-Type: application/json" -d '{}'
```

Ответ `{"code":422,"error_code":"anonymous_provider_disabled"}` означает,
что переключатель не сохранён, как бы он ни выглядел на экране.

Отдельно: у **Site URL** своя кнопка сохранения, независимая от списка
Redirect URLs. Список может сохраниться, а Site URL — нет.

### 2.2. В письме приходит ссылка, а не код

Если приложение просит шестизначный код, а человеку приходит ссылка —
дело не в коде приложения.

**На встроенной отправке шаблоны писем менять нельзя.** В дашборде на
странице шаблонов написано прямо: `Set up custom SMTP to edit templates`.
Стандартный шаблон содержит `{{ .ConfirmationURL }}`, то есть ссылку.

Чтобы в письме был код, шаблон должен использовать `{{ .Token }}`, а для
этого нужен свой SMTP (часть 3).

**Что делать, пока SMTP нет.** Ничего не переделывать: переход по ссылке
и ввод кода приводят к одному и тому же состоянию сессии. Экран входа
должен принимать оба пути и говорить о них честно — «если в письме
ссылка, перейдите по ней; если код, введите ниже».

Это не костыль. Экран, производный от **состояния сессии**, а не от
запомненного номера шага, переживает и переход по ссылке, и перезапуск
приложения посреди входа, и открытие письма на другом устройстве.

### 2.3. Лимит писем — 2–3 в час

Встроенная отправка заявлена как «только для разработки». Точную цифру
Supabase не публикует, порядок — несколько писем в час на проект.

Хватает, чтобы проверить вход. **Не хватает на демо**, где к продукту
подойдут пять человек подряд. Обнаруживается это в худший момент: письма
просто перестают приходить, без ошибки в приложении.

### 2.4. Confirm email ломает регистрацию по паролю

`Authentication → Sign In / Providers → Confirm email` включён по умолчанию.

При нём `signUp({ email, password })` возвращает **пользователя, но не
сессию**: войти можно только после перехода по письму.

Код вида

```ts
const { error } = await supabase.auth.signUp({ email, password });
if (error) throw error;
await doSomethingAuthenticated();   // ← упадёт
```

падает на второй строке с ошибкой про отсутствие авторизации — и человек
видит невнятное сообщение вместо «проверьте почту».

Правильно:

```ts
const { data, error } = await supabase.auth.signUp({ email, password });
if (error) throw error;
if (!data.session) return 'needs_confirmation';   // сессии ещё нет
```

Это не ошибка, а путь на шаг длиннее, и выглядеть он должен
соответственно.

### 2.5. Ссылка ведёт не туда

Если Site URL не настроен, ссылка из письма уводит на адрес по умолчанию,
и человек оказывается неизвестно где с работающей сессией — но не в вашем
приложении.

### 2.6. Кнопка со ссылкой на localhost в Telegram

Смежная ловушка, если рядом есть бот. Telegram отклоняет inline-кнопку с
адресом `localhost` («Wrong HTTP URL») и отклоняет **всё сообщение
целиком**, а не одну кнопку. Снаружи бот выглядит молчащим при исправном
polling.

## Часть 3. Свой SMTP

Нужен для продакшна всегда. Даёт три вещи сразу: снимает лимит,
разблокирует шаблоны (то есть код вместо ссылки) и позволяет писать с
собственного домена.

### Порядок

1. Завести аккаунт у почтового провайдера (Resend — 3000 писем в месяц
   бесплатно; подойдёт любой с SMTP).
2. Подтвердить домен отправителя — записи DNS. Без этого письма уходят в
   спам, и это единственный по-настоящему долгий шаг: DNS обновляется
   до нескольких часов.
3. `Project Settings → Authentication → SMTP Settings` — хост, порт,
   логин, пароль, адрес и имя отправителя.
4. После сохранения станут доступны шаблоны: `Authentication → Email
   Templates`.

### Шаблон с кодом

Вкладка **Magic Link**, заменить содержимое:

```html
<h2>Название продукта</h2>
<p>Ваш код для входа:</p>
<p style="font-size:28px;letter-spacing:4px;font-weight:600">{{ .Token }}</p>
<p>Код действует один час. Если вы его не запрашивали — удалите письмо.</p>
```

Ключевое — `{{ .Token }}` вместо `{{ .ConfirmationURL }}`.

Шаблонов несколько (Confirm signup, Magic Link, Change email, Reset
password), и правится каждый отдельно. Меняйте тот, который относится к
вашему сценарию: `signInWithOtp({ email })` использует **Magic Link**.

## Часть 4. Как проверять, не дожидаясь письма

Цепочка состоит из звеньев: приложение отправило запрос → Supabase принял
→ письмо ушло → дошло → человек перешёл. Когда «вход не работает», важно
знать, какое звено молчит.

**Приняли ли запрос** — видно сразу, без почты:

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  -X POST "https://<ref>.supabase.co/auth/v1/otp" \
  -H "apikey: <publishable-key>" -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","create_user":true}'
```

`200` означает, что приложение и Supabase ни при чём, и разбираться надо
с доставкой. Ошибка означает обратное.

**Что доступно после входа** — проверяется анонимной сессией, письмо для
этого не нужно вовсе:

```bash
R=$(curl -s -X POST "https://<ref>.supabase.co/auth/v1/signup" \
     -H "apikey: <key>" -H "Content-Type: application/json" -d '{}')
T=$(echo "$R" | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -s "https://<ref>.supabase.co/rest/v1/<таблица>?select=*" \
  -H "apikey: <key>" -H "Authorization: Bearer $T"
```

**Осторожно с кодировкой на Windows.** Консоль по умолчанию в cp1251, и
кириллица в теле запроса через `curl` уезжает не в UTF-8. Проверка тогда
показывает ошибку там, где её нет. Для запросов с русским текстом берите
Python с явным `.encode('utf-8')`, а не командную строку.

## Чек-лист переноса

- [ ] Site URL — адрес приложения, **Save changes нажата**
- [ ] Redirect URLs — каждый в своём поле, включая `scheme://**` для мобильного
- [ ] Anonymous sign-ins — если нужен, и проверен запросом, а не глазами
- [ ] Confirm email — решить, включён ли, и обработать отсутствие сессии в коде
- [ ] Экран входа принимает и ссылку, и код
- [ ] Перед демо или пилотом — свой SMTP
